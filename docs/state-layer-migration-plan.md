# خطة بناء طبقة الحالة (State Layer) — تطبيق الموبايل

## الوضع الحالي

- **أكتر من ١٨٠ استدعاء API مباشر** موزّعين على ~٤٠ ملف واجهة، مع `setState` (٢٧٠ مرة).
- **٤ Providers** (`Auth`, `Client`, `Contract`, `Notification`) مسجّلين في `main.dart` و**مش مستخدمين ولا مرة** — الوحيد الشغّال فعليًا هو `LocaleProvider`.
- **صفر Models** — كل البيانات `Map<String, dynamic>` و`dynamic`.
- **التغطية بالاختبارات**: ٩٦ اختبار، بس مركّزة في `login` و`forgot-password` و`create-client` والـ widgets الصغيرة. الشات والعقود والدفعات والداشبورد **تغطيتهم صفر**.

النقطة الأخيرة دي هي أهم حاجة في الخطة كلها: هي اللي بتحدد الترتيب وسرعة الشغل.

---

## هل هيبوظ المشروع؟

**لو اتعملت دفعة واحدة (rewrite): أيوة، وبشكل وحش.**
٨٥٪ من الشاشات دي مفيش حاجة بتحرسها. لو اتغيّر منطق تحميل البيانات فيها كلها مرة واحدة، الأعطال هتظهر عند المستخدم، مش عندك.

**لو اتعملت بالتدريج: لأ.**
والسبب مبدأ واحد بسيط:

> في أي لحظة، الكود القديم يفضل شغّال لحد ما البديل الجديد يثبت إنه شغّال. مانمسحش حاجة قبل ما نتأكد.

ده معناه إن المشروع بيفضل قابل للتشغيل والشحن في كل لحظة من مراحل النقل. مفيش لحظة "نص مكسور".

### إيه اللي ممكن يضيع (والعلاج)

| الخطر | العلاج |
|---|---|
| شاشة بتعمل تحويل خاص للبيانات (فلترة/ترتيب) بيتنسى في النقل | اختبار توصيفي (characterization test) للشاشة **قبل** ما نلمسها |
| حالات دفاعية زي `safeList()` و`?? []` بتتشال بالغلط | تتنقل جوه الـ Model نفسه في `fromJson` — مكان أنضف ليها |
| رسائل خطأ أو حالات تحميل مختلفة بين الشاشات | توحّد عمدًا في الـ Provider، ودي تحسين مش خسارة |
| سلوك offline / cache ضمني | يتوثّق في الـ Repository ويتغطى باختبار |

## البنية المستهدفة

```
lib/
  models/            ← جديد: كلاسات بيانات + fromJson/toJson
    client.dart
    contract.dart
    payment.dart
    ...
  data/              ← جديد: كل استدعاءات الـ API، مجمّعة حسب المجال
    client_repository.dart
    contract_repository.dart
    ...
  providers/         ← موجود: يتوسّع ويتوصّل فعليًا
  features/          ← الواجهات: تقرا من Providers، مابتنادي API خالص
  core/
    api_client.dart  ← يفضل زي ما هو، بس مايتنادىش من الواجهات
```

**القاعدة النهائية**: `features/` مايبقاش فيها ولا `_api.get(...)`. لو موجود، يبقى النقل ما خلصش.

## الترتيب — شرائح رأسية (Vertical Slices)

كل شريحة بتاخد مجال واحد كامل من أول الـ Model لحد الشاشة. الترتيب من الأأمن للأخطر:

| # | الشريحة | استدعاءات | التغطية الحالية | الملاحظة |
|---|---|---|---|---|
| ٠ | **Auth** | ٤ | جيدة (login + forgot-password) | `AuthProvider` مكتوب ومتنستش توصيله — أصغر شريحة وأأمنها |
| ١ | **Clients** | ١٣ | متوسطة (create-client) | `ClientProvider` موجود جزئيًا |
| ٢ | **Managers** | ٩ | صفر | مجال صغير ومعزول |
| ٣ | **Notifications** | ٤ | صفر | صغير، و`NotificationProvider` موجود |
| ٤ | **Files** | ٨ | صفر | متوسط |
| ٥ | **Approvals** | ٩ | صفر | متوسط |
| ٦ | **Meetings + Calendar** | ١٢ | صفر (فيه اختبارات لـ `meeting_helpers`) | متوسط |
| ٧ | **Contracts** | ٢١ | صفر | كبير، وفيه تكرار بين ملفين |
| ٨ | **Payments** | ١٣ | صفر | كبير، حسّاس (فلوس) |
| ٩ | **Settings** | ٢٠ | صفر | كبير ومتشعّب |
| ١٠ | **Dashboard** | ٢٠ | صفر | بيجمّع من كل المجالات — لازم يتأخّر لحد ما اللي تحته يخلص |
| ١١ | **Chat** | ٢١ | صفر | الأخطر: أكبر ملفين، مكرّرين، وفيهم realtime. يتعمل مع توحيد الشاتين في نفس الوقت |

**ليه Auth الأول؟** أصغر شريحة، أحسن تغطية اختبارات، والـ Provider مكتوب خلاص — يعني بتتعلم الروتين على أرخص مثال ممكن قبل ما تدخل على حاجة كبيرة.

**ليه Dashboard والـ Chat آخر حاجة؟** الداشبورد بيستهلك بيانات كل المجالات التانية، فلو اتنقل الأول هيتكتب مرتين. والشات هو أكبر وأخطر جزء وتغطيته صفر.

## وصفة الشريحة الواحدة (تتكرر ١٢ مرة)

كل خطوة تخلص بـ commit مستقل.

**١. اختبار توصيفي أولًا**
اكتب اختبار يوثّق سلوك الشاشة **الحالي** (إيه اللي بيتنادى، إيه اللي بيتعرض). مش بتصلّح حاجة هنا — بتثبّت الوضع القايم عشان تعرف لو كسرته.

**٢. الـ Model**
```dart
class Client {
  final int id;
  final String companyName;
  final String? avatarUrl;

  const Client({required this.id, required this.companyName, this.avatarUrl});

  // كل الحماية الدفاعية اللي كانت متناثرة في الواجهات تتجمّع هنا.
  factory Client.fromJson(Map<String, dynamic> json) => Client(
    id: json['id'] as int,
    companyName: json['company_name'] as String? ?? '',
    avatarUrl: json['avatar_url'] as String?,
  );
}
```
+ اختبار وحدة لـ `fromJson` بحقل ناقص وبحقل نوعه غلط.

**٣. الـ Repository**
```dart
class ClientRepository {
  final ApiClient _api;
  ClientRepository({ApiClient? api}) : _api = api ?? ApiClient();

  Future<List<Client>> fetchAll() async {
    final res = await _api.get('/clients');
    return safeList(res['clients']).map((j) => Client.fromJson(j)).toList();
  }
}
```
+ اختبار بـ `mocktail` (نفس نمط `test/unit/api_client_test.dart` الموجود).

**٤. الـ Provider**
يستخدم الـ Repository، ويعرض `data / isLoading / error`. الأربعة الموجودين دلوقتي هما القالب.

**٥. نقل الشاشة**
شاشة واحدة بس في المرة. شيل `_api.*` و`setState`، استخدم `context.watch<XProvider>()`.

**٦. تحقق**
`flutter analyze` + `flutter test` + تشغيل الشاشة يدويًا. لو الاختبار التوصيفي (خطوة ١) لسه أخضر، يبقى السلوك ما اتغيرش.

**٧. كوميت**، وبعدين الشاشة اللي بعدها في نفس المجال.

**تمام الشريحة (Definition of Done)**: مفيش `_api.` في ملفات المجال ده، الاختبارات خضرا، والشاشة اتجربت على جهاز.

## قواعد السلامة

1. **برانش لكل شريحة**، مش لكل المشروع. `git checkout master` بيرجّعك في ثانية.
2. **ماتمسحش القديم قبل الجديد** — الـ `ApiClient` يفضل زي ما هو طول الوقت.
3. **مفيش شريحتين مفتوحين في نفس الوقت**.
4. **الشاشة اللي تغطيتها صفر ماتتلمسش قبل ما يتكتبلها اختبار.**
5. **الـ CI هو الحكم** — `analyze` + `test` + `build apk` لازم يبقوا خُضر قبل أي دمج.

## توقّع واقعي

- الشرائح ٠–٣ (Auth, Clients, Managers, Notifications): ٣٠ استدعاء، مجالات صغيرة ومعزولة. أسرع جزء، وبيبني الروتين.
- الشرائح ٤–٩: الشغل الأساسي، أغلبه ميكانيكي متكرر بس محتاج اختبارات من الأول.
- الشريحتين ١٠–١١ (Dashboard, Chat): الأصعب. الشات لوحده يعتبر مشروع صغير لأنه بيتضمّن توحيد ١٢٢٠ سطر مكرّرين.

**ماينفعش يتعمل في جلسة واحدة.** الخطة دي متصممة إنها تتوقف عند أي شريحة والمشروع يفضل سليم وقابل للشحن.

## مكسب جانبي

لما الشرائح دي تخلص، **٤ من الـ ٥ ملاحظات** اللي المراجع الخارجي هيقولها بتتحل مع بعض:
Models، طبقة الحالة، تكرار الشات، وتقسيم الملفات الضخمة (بتتقلّص لوحدها لما منطق البيانات يخرج منها).
