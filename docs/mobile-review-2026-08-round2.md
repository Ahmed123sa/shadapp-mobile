## ثانيًا: النتائج الجديدة

المراجعة الأولى كانت مركّزة على طبقة الـ API والراوتر. الجولة دي دخلت على **طبقة الـ realtime** (`reverb_service.dart`) — وهي أكبر منطقة في المشروع لسه مالهاش تغطية سلوكية. أغلب اللي تحت طلع من هناك.

### ١. الـ WebSocket مابيتقفلش عند تسجيل الخروج — وده بقى أسوأ بعد إصلاحنا

`ReverbService.disconnect()` بتتنادى من مكانين بس، الاتنين `dispose()` بتوع شاشات الشات:

- `chat_page.dart:146`
- `chat_tab.dart:382`

**ولا واحد من التلات مسارات بتوع تسجيل الخروج بينادي عليها**:

- `client_dashboard_screen.dart:347-349`
- `am_dashboard_page.dart:210-212`
- `client_onboarding_screen.dart:216-218`

كلهم بيعملوا `clearToken()` ثم `context.go('/login')` وبس. النتيجة إن بعد الخروج: السوكيت فاضل مفتوح، `_currentUserId`/`_currentWorkspaceId` لسه متسجلين، وتايمر الـ ping شغال كل ٢٥ ثانية.

ده كان **تسريب موارد صامت** قبل الجولة الأولى. دلوقتي بقى مرئي للمستخدم، والسبب إصلاحنا إحنا:

```
المستخدم يخرج → السوكيت لسه مفتوح بهوية قديمة
   → السوكيت يقع (تغيير شبكة/الموبايل يروح للخلفية)
   → _reconnect() بعد ١٠ ثواني (reverb_service.dart:226)
   → connection_established → _subscribePrivateChannel (سطر ١٩١)
   → POST /broadcasting/auth من غير توكن → 401
   → api_client.dart:367 → onSessionExpired()
   → main.dart:101 → router.go('/login')
```

يعني المستخدم قاعد بيكتب بياناته في شاشة الدخول، والشاشة بتتبني من جديد وتمسح اللي كتبه. `go('/login')` وهو أصلًا على `/login` بيعمل route جديد يعني `TextEditingController` جديد.

**قبل الجولة الأولى** الـ 401 ده كان بيتلوج ويُنسى (`_subscribePrivateChannel` بيلقفه في سطر ٢٠٧). إحنا خلّينا كل 401 يوجّه لـ `/login`، فطلع التداخل ده.

**الحل** — سطر واحد في كل مسار خروج:
```dart
ReverbService().disconnect();   // قبل clearToken()
```
`disconnect()` بيصفّر `_currentWorkspaceId`/`_currentUserId` (سطر ٢٤٧-٢٥١)، وده بيوقف حلقة `_reconnect` من جذرها لأن شرطها في سطر ٢٢٨-٢٣٦ بيبص على الاتنين دول.

### ٢. سباق في إعادة الاتصال: `onError` و`onDone` كلاهما ينادي `_reconnect()`

`reverb_service.dart:156-157`:

```dart
onError: (_) => _reconnect(),
onDone:  () => _reconnect(),
```

في ستريمات الـ WebSocket، الخطأ عادةً بيولّد الاتنين مع بعض. وكل `_reconnect()` (سطر ٢٢٦) هو `Future.delayed(10s)` **مالوش أي وسيلة إلغاء ولا حارس "أنا أصلًا بعيد الاتصال"**. فبقى عندك سلسلتين إعادة اتصال متوازيتين، كل واحدة بتنادي `WebSocketChannel.connect` وبتسجّل `stream.listen` خاص بيها.

`_connectAndListen` بيبدأ بـ `_disconnect()` (سطر ١٠٢) بس ده مش كفاية لما الاتنين شغالين في نفس الوقت — الـ listener بتاع الخاسر فاضل حي.

كمان: التأخير ثابت ١٠ ثواني، مفيش backoff. سيرفر واقع = نداء كل ١٠ ثواني بلا نهاية.

### ٣. `addMessage` بتضيف من غير فحص التكرار، جنب `updateMessage` اللي بتفحص

نفس البلوك، في الملفين (`chat_page.dart:92-101` و`chat_tab.dart:103-112`):

```dart
addMessage:    (msg) => _messages.add(msg),                          // ← بتضيف على طول
updateMessage: (msg) {
  final idx = _messages.indexWhere((m) => m['id'] == msg['id']);     // ← بتدوّر بالـ id
  if (idx >= 0) _messages[idx] = msg;
},
```

مسار التعديل واعي بالـ `id`، مسار الإضافة لأ. مع بند ٢ فوق (listener مكرر) النتيجة **رسالة بتظهر مرتين في الشات**.

مش صدفة إن `onNotificationReceived` وحده عنده حماية من التكرار (`_lastNotifTime`، سطر ١٥٠) — يبدو إنها اتحطت كعلاج لعرَض من نفس المرض، بدل ما السبب نفسه يتصلح.

اللي غطّى على ده لحد دلوقتي إن `RealtimePoller` بيعمل `_load()` كامل كل دقيقة (`realtime_poller.dart:26`)، فالنسخة المكررة بتختفي لوحدها بعد شوية.

**الحل**: نفس فحص الـ `id` اللي في `updateMessage`:
```dart
addMessage: (msg) {
  if (_messages.any((m) => m['id'] == msg['id'])) return;
  _messages.add(msg);
},
```

### ٤. حراسة الأدوار لسه مش موجودة — إحنا عملنا نص P0 ١ بس

التقرير الأول قال في P0 ١ حاجتين: (أ) مفيش redirect لانتهاء الجلسة، (ب) مفيش guard على المسارات حسب الدور. **إحنا عملنا (أ) بس.**

`router.dart:32-43` بيفرّق بين "داخل" و"مش داخل" وخلاص. عميل مسجّل دخوله يقدر لسه يفتح `/am/settings` أو `/am/audit-logs` من deep link. الباك اند بيرفض بـ 403 (مفيش تسريب بيانات)، لكن اللي بيتعرض شاشة إدارية مكسورة بدل ما يترد لمكانه.

ده مالوش عذر إنه اتنسي — التقرير الأول ذاكره صراحة. الحل امتداد بسيط للـ redirect الموجود: قايمة بمسارات الـ staff، ولو الدور `client`/`sub_user` يترد لـ `/dashboard`.

### ٥. الـ redirect الجديد نفسه مالوش ولا تست

`createRouter` بقى فيه منطق بيتنفذ **على كل عملية تنقل في التطبيق**، وصفر تغطية. ده أخطر سطح جديد ضفناه في الجولة الأولى.

الحالات اللي محتاجة تستات:

- مش داخل + مسار محمي → `/login`
- مش داخل + `/login` → `null` (مايعملش حلقة)
- داخل + `/login` → داشبورده حسب الدور
- داخل كـ `sub_user` + `/login` → `/dashboard` (مش `/am/dashboard`)
- داخل + مسار محمي → `null`

راجعت الحالات دي يدويًا ومنطقها سليم — بس "راجعتها بعيني" مش بديل عن تست، وده بالظبط اللي التقرير الأول اتقال فيه عن `main.dart`.

## اللي اتحسّن فعلًا

- **الأخطاء بقت مرئية.** صفر `catch` فاضية، صفر `debugPrint`. كل فشل بيوصل Crashlytics. ده باين في مخرجات التستات نفسها دلوقتي (`[client_profile_tab._load] Server error`) — علامة إن التوجيه شغّال.
- **`notification_routing.dart`** — استخراج نضيف: دالتين نقيتين، تست يمنع رجوع باج الـ `sub_user`، و`main.dart` بقى wrapper سطر واحد.
- **`RealtimePoller`** (`realtime_poller.dart`) أنضف حاجة قريتها في المشروع — منطق صغير، موثّق بالسبب مش بالوصف، وقابل للحقن للاختبار. لو الكود كله بالمستوى ده مكنش فيه تقرير تاني.
- **التعليقات التفسيرية** فضلت متماسكة حتى في الكود اللي إحنا كتبناه الجولة اللي فاتت. الملفات بتشرح **ليه**، وده اللي خلّى المراجعة دي أسرع من الأولى.
